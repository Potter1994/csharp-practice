# Day 4 筆記:作業系統 — Process / Thread

## 練習 1:Process vs Thread

### Process(行程)

**Process = 一個正在執行中的程式。**

同一個程式可以有很多個 Process —— 例如 Chrome 每個分頁大致就是一個獨立的 Process,
所以一個分頁當掉不會拖垮整個瀏覽器。

作業系統給每個 Process:

1. **獨立的記憶體空間**(最關鍵)
2. 開啟的檔案、網路連線等資源
3. 至少一條執行緒(primary thread)

### Thread(執行緒)

**Thread = Process 內部的一條執行路線。**

```
電腦
├── Process(Chrome)              ← 獨立的記憶體空間
│     ├── Thread 1
│     ├── Thread 2                ← 共享同一塊記憶體
│     └── Thread 3
└── Process(VS Code)             ← 另一塊獨立的記憶體空間
      ├── Thread 1
      └── Thread 2
```

> **Process 是容器,Thread 住在裡面。**

### 記憶體在兩個層級的狀況

```
Process 的記憶體空間
┌────────────────────────────────────────┐
│  Heap(所有 Thread 共享)                │
│  ┌──────┬──────┬──────┐                │
│  │物件A │物件B │物件C │                 │
│  └──────┴──────┴──────┘                │
│                                        │
│  Thread 1 的 Stack   Thread 2 的 Stack  │
│  ┌──────────────┐   ┌──────────────┐   │
│  │ 區域變數      │   │ 區域變數      │   │  ← 各自獨立
│  │ 呼叫框架      │   │ 呼叫框架      │   │
│  └──────────────┘   └──────────────┘   │
└────────────────────────────────────────┘
```

**每條 Thread 有自己的 Stack,但共享整個 Heap。** 這解釋了兩件事:

- **為什麼區域變數安全** — 在各自的 Stack 上,互不干擾
- **為什麼會有 race condition** — Heap 上的物件是共享的,兩條 Thread 可能同時改同一個東西

### ⚠️ 兩種「隔離」性質完全不同

| | 隔離機制 |
|---|---|
| **Process 之間** | **硬體強制隔離**(CPU 的 MMU 把虛擬位址對應到不同實體記憶體)。想讀也讀不到 |
| **Thread 之間** | **完全沒有隔離**。只是區域變數在語言層面「看不到」對方而已 |

同一個 Process 裡的兩條 Thread,記憶體是完全開放的:

```csharp
int counter = 0;                          // 區域變數
var t = new Thread(() => counter++);      // lambda 捕捉了它
t.Start();                                // 另一條 thread 真的在改它
```

> **正因為 Thread 之間毫無防護,race condition 才可能發生。**

## 練習 1(續):I/O bound vs CPU bound

### 「bound」的意思

**bound = 被……限制住**,講的是**瓶頸在哪裡**。

| 名詞 | 瓶頸 | CPU 的狀態 |
|---|---|---|
| **CPU bound** | CPU 運算能力 | 一直在忙 |
| **I/O bound** | 輸入/輸出的等待(網路、硬碟、資料庫) | 大多在閒著 |

### 下載檔案時 CPU 在做什麼

```
① CPU 對網路卡說「幫我抓這個檔案」        ← 約 0.001 毫秒
② 等資料從網路傳過來 ……                  ← 約 200 毫秒  ★ CPU 完全沒事做
③ 資料到了,CPU 處理一下                  ← 約 0.1 毫秒
```

**步驟 ② 佔了 99.9% 的時間,而 CPU 在發呆。**

完整的硬體流程:

```
① 你的程式        socket.ReadAsync()
                        │
② 系統呼叫        ─────▶ 作業系統核心(kernel)
                        │
③ 核心指揮        ─────▶ 網路卡驅動程式 ──▶ 網路介面卡(NIC)
                        │
④ 執行緒被掛起     ◀─────┤  OS 標記成「等待中」,從排程器移出 → 不佔 CPU
                        │
   ═══════ 這段時間 CPU 去做別的事,或閒置 ═══════
                        │
⑤ 網路卡自己收資料  ←──── 網際網路        (CPU 沒有參與)
⑥ DMA 直接寫入記憶體 ───▶ RAM             (CPU 沒有參與)
⑦ 網路卡發出中斷     ───▶ CPU「資料好了」
⑧ OS 喚醒那條執行緒  ───▶ 程式繼續跑
```

三個關鍵:

- **網路卡是獨立硬體**,有自己的處理器。CPU 只負責下訂單和收貨
- **DMA(直接記憶體存取)** — 資料進記憶體不經過 CPU。這是「CPU 能真的閒著」的硬體基礎
- **中斷(interrupt)** — 網路卡完成後主動通知 CPU,不需要輪詢

### 執行緒的三種狀態

```
執行中 (Running)   ← 正在某顆 CPU 核心上跑
就緒   (Ready)     ← 排隊等 CPU
等待中 (Blocked)   ← 在等 I/O,完全不排隊、不佔 CPU  ★
```

等待中的執行緒**消耗零 CPU** —— 這就是為什麼等待可以重疊。
而算質數的執行緒永遠在「執行中」或「就緒」,它們是**真的在搶 CPU**。

### 結論

**8 顆核心,開 100 條執行緒算質數 → 不會更快**

- 8 顆核心最多同時算 8 份工作,再多開也變不出第 9 顆核心
- 而且 OS 要在 100 條之間輪流切換(**context switch**),保存與還原狀態本身就吃 CPU
- **反而更慢**

**開 100 條執行緒下載 100 個檔案 → 會更快,但不是線性的**

一開始有效(等待重疊),到某個點就打平,再多甚至會下降:

```
下載速度
   ▲
   │        ╭────────────  ← 撞到頻寬上限,不再增加
   │      ╱
   │    ╱                  ← 這段有效:等待在重疊
   │  ╱
   └────────────────────▶ 執行緒數量
      1   10   100  1000
```

其他上限:

| 上限 | 說明 |
|---|---|
| 網路頻寬 | 100 Mbps 就是 100 Mbps,開再多只是每條分到更少 |
| 網路卡處理能力 | 硬體本身的極限 |
| 對方伺服器 | 可能限制同 IP 連線數,或把你當攻擊擋掉 |
| 作業系統資源 | socket 數量、檔案控制代碼上限 |
| 執行緒本身的成本 | 每條預設保留約 1 MB stack,加上核心簿記資料 |

> **精確的說法:多執行緒對 I/O 有效,是在「瓶頸轉移到別的地方之前」有效。**
> 瓶頸從「等待」變成「頻寬」之後,加執行緒就沒用了。

### 生活比喻

| | 比喻 | 多找人幫忙有用嗎 |
|---|---|---|
| **I/O bound** | 煮泡麵 — 倒完水要等 3 分鐘 | ✅ 一個人可以同時等 10 碗,等待會重疊 |
| **CPU bound** | 切菜 — 得一刀一刀切 | ⚠️ 要有 10 把刀(核心)才有用,10 個人搶 1 把刀反而更慢 |

## 為什麼需要 async

每條執行緒約 1 MB stack。若 API 要同時處理一萬個連線,
一萬條執行緒光 stack 就要 10 GB —— 而它們 99% 的時間只是躺著等。

> **純粹為了「等待」而養一條執行緒,太貴了。**

`async/await` 解決的正是這件事:等待時連執行緒都不需要佔著。

## 延伸:`await` 不等於開新執行緒

### 常見誤解

> 「`async/await` 是非同步,所以它會開一條新的執行緒去跑。」

錯。`await` **本身不會建立任何執行緒**。會被誤解通常是因為看到 `Task.Run`
確實用了執行緒,就以為所有 `Task` 都一樣。

### 實際機制:等待期間零執行緒

不是只要有非同步就要開一條新的 thread。`async/await` **等待期間並沒有任何一條
執行緒在等**,拿到結果後會從現有的執行緒中選一條,繼續執行 `await` 後面的程式碼。

> **★ 等待期間 0 條執行緒被佔用。**

拆解 `await Task.Delay(500)` 發生了什麼:

```
① 方法在目前的執行緒上「同步」執行,直到碰到 await
② 向作業系統註冊一個計時器(或對 I/O 而言:註冊完成通知)
③ 方法「暫停」,控制權還給呼叫者 → 這條執行緒去做別的事

   ═══ 這 500 毫秒之間,零條執行緒被佔用 ═══

④ 計時器到期 / I/O 完成 → 作業系統發出中斷通知
⑤ 執行環境把「await 之後的那段程式碼」排進執行緒集區
⑥ 某條集區執行緒撿起來繼續跑
```

關鍵在 ③ 到 ④ 之間:**沒有人在「等」**。沒有一條執行緒坐著數秒數,
只有一個註冊在作業系統的計時器 / I/O 完成通知。

### 證據:練習 3 的執行緒 ID 觀察

```
主執行緒 ID = 1
  A await 之前 : Thread 1
  B await 之前 : Thread 1      ← 三個都在主執行緒上「開始」
  C await 之前 : Thread 1
  A await 之後 : Thread 5
  C await 之後 : Thread 5      ← 三個都在同一條集區執行緒上「恢復」
  B await 之後 : Thread 5

執行緒集區的執行緒數 = 2        ← 3 個任務,只用了 2 條執行緒
```

三點可以直接讀出來:

| 觀察 | 意義 |
|---|---|
| await 之前全是 Thread 1 | 方法一開始是**同步**執行的,沒有換執行緒 |
| await 之後變成 Thread 5 | 延續(continuation)在**集區執行緒**上恢復,不是原本那條 |
| 3 個任務只用 2 條執行緒 | **不存在「一個任務一條執行緒」這回事** |

### `await` vs `Task.Run` —— 最關鍵的對比

```csharp
await httpClient.GetStringAsync(url);       // 不佔執行緒(I/O 由硬體處理)
await Task.Run(() => 算一百萬個質數());      // 借一條集區執行緒,而且它在燒 CPU
```

**兩個都寫 `await`,但一個是「等別人」,一個是「請人幫我算」。**

| | 有執行緒在忙嗎 | 適用 |
|---|---|---|
| `await` I/O 操作 | ❌ 零條 | I/O bound |
| `await Task.Run(...)` | ✅ 一條在燒 CPU | CPU bound |

所以:

```csharp
await Task.Run(() => httpClient.GetStringAsync(url));   // ❌ 多此一舉
await httpClient.GetStringAsync(url);                    // ✅
```

I/O 本來就不需要執行緒,包一層 `Task.Run` 只是「借一條集區執行緒來發出請求,
然後立刻歸還」—— 多了開銷,沒有好處。

### `Task.Run` 也不是「開新執行緒」

實測 100 個 `Task.Run`(10 核心機器):

```
100 個 Task.Run   → 實際用了 11 條執行緒(每條重用約 10 次)
100 次 new Thread → 用了 100 條執行緒(每次都是新的)
```

`Task.Run` 是**把工作丟進執行緒集區排隊**,集區重複使用既有的執行緒。
只有 `new Thread` 才是真的每次建立新的。

理由是開執行緒很貴:1 MB stack + 核心資料結構 + 約 0.1~1 毫秒的建立成本。

### 跟 JavaScript 的差異

| | JavaScript | C# |
|---|---|---|
| 等待期間佔執行緒嗎 | ❌ | ❌ |
| 底層 OS 機制 | kqueue / epoll / IOCP | **相同** |
| **完成後在哪繼續** | **唯一的主執行緒**(微任務佇列) | **執行緒集區任一條** |
| 需要擔心 race condition | ❌ 只有一條執行緒 | ✅ 可能真的並行 |
| 能真正平行運算嗎 | ❌(要用 Web Worker) | ✅ `Task.Run` |

> `Promise` 是「**等待**的抽象」;`Task` 是「**工作**的抽象」——
> 而工作可能是等待,也可能是運算。

實務影響:C# 裡 `await` 之後的程式碼可能跑在**不同執行緒**上,
所以碰到共享狀態時,練習 2 的 race condition 問題會回來。JS 沒有這個顧慮。

## ⚠️ 實務陷阱:執行緒集區飢餓

集區執行緒被**阻塞**時,它不能去撿下一個工作,而集區**每秒只補 1~2 條**新的。

```csharp
// ❌ 絕對不要在非同步路徑上阻塞
var result = httpClient.GetStringAsync(url).Result;   // 阻塞集區執行緒
task.Wait();                                           // 同上
Thread.Sleep(1000);                                    // 同上
```

同時來 100 個這種請求會發生:

```
前 10 個佔滿所有集區執行緒 → 全部卡住不動
剩下 90 個在佇列裡排隊
集區每秒只補 1~2 條 → 要一分鐘才消化得完
→ API 看起來整個掛掉,但 CPU 使用率是 0%
```

> **規則:在非同步的路徑上,永遠用 `await`,絕不用 `.Result` 或 `.Wait()`。**

這是 ASP.NET Core 最常見的效能事故。

### 三者的分工

| 情境 | 用什麼 |
|---|---|
| **I/O**(網路、檔案、資料庫) | 直接 `await`,不要包 `Task.Run` |
| **CPU 工作**,想搬離目前執行緒 | `Task.Run` |
| **長時間持續的背景工作** | `new Thread`,或 `TaskCreationOptions.LongRunning` |

最後一項的理由:長時間執行的工作若佔著集區執行緒不放,
等於永久減少集區容量 —— 這種就該用專屬的執行緒。
